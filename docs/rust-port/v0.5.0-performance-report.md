## Optimization Disposition

Four refresh/search-side optimization candidates were evaluated before this report:

- Runtime refresh mark document-lock split: rejected. It reduced no clear hot cost and worsened full benchmark throughput.
- Deferred native replay lock split: rejected with the same benchmark run because three-node throughput and refresh p99 regressed.
- Dirty shard refresh mark without document lookup: rejected with the same benchmark run; the full workload regressed.
- Native refresh duplicate append-only condition removal: no new change needed; the duplicate condition was already absent in the current tree.

The rejected benchmark artifact is `target/search-benchmark-matrix-refresh-locksplit-current-full-20260830/summary.json`.

Rejected result versus the accepted baseline:

- Single-node throughput: 666.252 ops/s baseline, 662.153 ops/s candidate.
- Three-node throughput: 851.496 ops/s baseline, 832.257 ops/s candidate.
- Three-node refresh p99: 26.727 ms baseline, 31.488 ms candidate.

## Current Bottleneck Read

The final benchmark no longer shows a measured OpenSearch-relative latency loss. The remaining work is compatibility and architecture, not a simple Rust hot-loop issue:

- Shard semantics should move further toward physical shard-local index/runtime state.
- API compatibility gaps should be prioritized by replacement and mixed-cluster impact, not by byte-for-byte index-level compatibility.
- Future feature changes must rerun the benchmark matrix and must either avoid or repair performance regressions before release.
